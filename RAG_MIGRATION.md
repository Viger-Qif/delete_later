# RAG: решение по старым карточкам

## Что является рабочим источником сейчас

В пользовательском интерфейсе используются семь отдельных методик. Для текущего этапа активна только SPIN.

Машинный слой не обязан повторять интерфейс справочника. Поэтому рабочий RAG остаётся отдельным слоем:

```text
человеческая методика SPIN
        ↓
нормализованные RAG-чанки
        ↓
BM25 / будущий hybrid retrieval
        ↓
оппонент, Фиделина, анализ, упражнения
```

Сейчас в `backend/app/knowledge/handbook.json` находятся 20 нормализованных SPIN-чанков. Это не старые 147 карточек и не пользовательский каталог.

## Что делать со старым `NegotiationLab-cards-expanded-v2.zip`

Старый пакет не импортируется в production напрямую.

Он полезен как:

- архив исходного контентного исследования;
- источник формулировок, плейбуков и упражнений;
- материал для будущей миграции остальных методик;
- источник контрольных запросов для benchmark.

Прямой импорт создаст несколько проблем:

- повторное появление технической «россыпи карточек»;
- конфликт между `method_id` с дефисами и подчёркиваниями;
- смешение глоссария, плейбуков и методических принципов;
- расхождение пользовательской статьи и RAG-ответов;
- преждевременное включение шести ещё не готовых методик.

## Текущее улучшение RAG

Индекс теперь учитывает не только `title`, `text` и `tags`, но также:

- `summary`;
- `method_id`;
- `stage`;
- `steps`;
- `phrases`;
- `antipatterns`;
- `checks`.

Это важно, потому что короткий запрос пользователя часто совпадает не с основным текстом чанка, а с его примером, проверкой или шагом.

Это небольшой smoke-benchmark, а не доказательство качества production-RAG. Перед подключением новых методик его нужно расширить размеченными запросами и проверкой нерелевантных попаданий.

## LLM-RAG слой v21.2

LLM не заменяет retrieval. Он получает ограниченный контекст после BM25-поиска и работает в разных режимах:

1. быстрый ход диалога — RAG помогает оппоненту и coach сохранять контекст этапа;
2. итоговый разбор — LLM обязан вернуть evidence с точной цитатой из транскрипта;
3. optional learning coach — пользователь сам просит объяснение ответа;
4. recommendation — LLM выбирает только из белого списка существующих SPIN-упражнений.

Каждый LLM-RAG ответ валидируется:

- `knowledge_refs` проверяются по существующим chunk ID;
- `exercise_id` проверяется по кандидатам текущего SPIN-трека;
- команды внутри retrieved текста игнорируются;
- при ошибке возвращается детерминированный rubric fallback;
- в ответе сохраняется `rag.chunk_ids`, чтобы видеть, чем был обоснован совет.

Такой режим оставляет дорогой LLM-вызов opt-in для упражнения и использует более тяжёлый вызов только там, где он действительно меняет учебное действие. Это соответствует рекомендациям оценивать не только retrieval recall, но также faithfulness, citation accuracy и изменение ответа ученика после обратной связи.
